# bug-finder

このスキルのゴールは、症状を消すことではなく、症状が出る理由を説明できる状態にすることである。原因を名指す前に、次を確認する。

- 報告された症状と、調査中に見つけた症状の一つひとつに、その原因からの筋道を書けるか。書けない症状が残るなら、原因は他にもある。
- 誤った値はどこで作られたか。その地点を通る前の値は正しかったか。
- その箇所だけを変えたとき、判定コマンドの結果は変わったか。

確かめていないことは「推定」と書く。症状を手元で出せず原因が推定のままなら、コードは変えずに修正案として示す。

## 進め方

各段階で分かったことを短くメモしながら進める。報告はこのメモから組み立てる。

### 1. 期待と実際を一文ずつに分ける

- 「何をしたら」「何が起きるはずで」「実際は何が起きたか」を、報告の言葉ではなく観測できる形で書く。例: 「15 km の経路で 240 円のはずが 320 円」。
- 条件を集める。入力、データ、環境、版、頻度、いつから起きているか。報告に無いものは推測で埋めず、手元で確かめるかユーザーに尋ねる。
- 報告者の原因の見立て (「キャッシュのせいでは」「サーバーが遅いからだ」) は仮説の一つとして扱う。採用も否定も観測で決める。

### 2. 手元で症状を出す

- 報告と同じ症状を、自分のコマンドで出す。出せたら、そのコマンドを以後の判定に使う。
- 一度しか出ない、たまにしか出ないなら、失敗率を測る。[references/flaky.md](references/flaky.md)
- 出せない場合は、環境の差 (版、設定、データ、実行順、並行度) を一つずつ相手の条件へ寄せる。それでも出ないなら、どこまで寄せたかを報告して止まる。コードは変えず、推定の原因と修正案を示す。
- 修正の前に、現状の数値や出力を記録しておく。修正後の比較に使う。

### 3. 仮説を並べ、仮説を区別する観測を選ぶ

- 候補を複数書き出す。一つに絞ると、合わない観測を見落とす。
- 観測は「どちらの仮説が正しいかで結果が変わるもの」を選ぶ。どちらでも同じ結果になる観測は時間の無駄である。
- 範囲を縮める手段を使い分ける。どれも [references/narrowing.md](references/narrowing.md) にある。
  - 動くケースと動かないケースの差を取る (入力、版、環境、データ)。
  - 入力やコードを削って、症状が残る最小の形にする。
  - 誤った値がどこから来たかを、使われた地点から作られた地点へ遡る。
- 「以前は動いていた」なら、変更履歴を先に調べる。[references/regressions.md](references/regressions.md)
- 例外がライブラリや生成コードの中で起きていても、その値を渡したのは呼び出し側であることが多い。[references/origin.md](references/origin.md)
- コードに誤りが見つからないなら、生成物、キャッシュ、設定、依存の版を疑う。[references/non-code-causes.md](references/non-code-causes.md)

### 4. 介入で原因を確定する

- 原因と考える箇所だけを変えて、手順 2 のコマンドで症状が消えることを確かめる。可能なら元に戻して症状が戻ることも確かめる。
- 確定した原因で、手順 1 で集めた条件をすべて説明できるか確かめる。「なぜテストは通っていたのか」「なぜこのテナントだけなのか」に答えられなければ、まだ途中である。

### 5. 同じ原因の広がりを調べる

- 同じ誤った値を使っている別の処理を探す。クラッシュしていないだけで、誤った出力を出している処理がよくある。
- 同じ書き方、同じ式、同じ前提を grep などで探す。コピーされた誤りは複数箇所にある。
- 見つけたものは、直すか、直さない理由を添えて報告する。

### 6. 原因が生まれた地点で直す

- 誤った値が入り込んだ地点、条件が抜けた地点で直す。値を使う側で辻褄を合わせると、他の使い手に誤りが残る。
- 外部から取り込んだコードや生成物は直接編集しない。呼び出し側、生成元、設定を直す。
- テストの期待値を書き換えて通すのは、期待値の方が誤っていると根拠を示せる場合だけである。
- 修正と一緒に、壊れていない変更まで戻さない。混ざったコミットは必要な部分だけ直す。
- 原因を再現するテストを足す。修正前に失敗し、修正後に通ることを確かめる。
- テスト全体を実行し、結果をそのまま報告する。
- 修正の作法の詳細は [references/fixing.md](references/fixing.md)。

### 急ぎで止血だけしたい場合

依頼が「とにかく今止めたい」「大きな作り直しはしない」で、小さく安全な根本修正では間に合わない場合は、応急処置にとどめる。何を選び、何を報告するかは [references/stopgap.md](references/stopgap.md)。

## 依頼の制約を守る

- 「原因だけ調べて」「コードは変えないで」と言われたら、ソースを編集しない。調査用の一時ファイルや出力は作業後に消す。
- 「このファイルには触らないで」と言われた範囲は、修正の候補からも外す。外さないと直せないなら、その理由を報告して判断を仰ぐ。
- 副作用のある操作 (外部への送信、データベースの更新、課金、メール送信) を調査のために実行しない。必要なら、止める手段か模擬環境を用意してから行う。
- 検索エンジンやチャットに送る文字列から、社内のホスト名、認証情報、顧客のデータを除く。
- ユーザーの未コミットの変更を消したり、調査用の変更と混ぜたりしない。版を切り替えるときは別の作業ツリーを使う。
- コミットは、ユーザーが求めたときか、依頼の内容がコミットを前提とするとき (「revert して」など) だけ作る。

## 報告

次の順で書く。短くてよいが、確かめたことと推定を分ける。

1. **原因**: どのファイルのどの処理が、どういう条件で、何を誤るか。
2. **根拠**: 症状を出したコマンドと結果、原因を変えたときの結果。複数の版や条件で確かめたなら、その結果を並べる。
3. **否定した仮説**: 報告者の見立てや、自分が調べて外した候補と、外した根拠。
4. **影響範囲**: 同じ原因で起きていた別の症状、同じ書き方の箇所、該当するデータ (どのテナント、どの経路など)。
5. **修正**: 何をどこで変えたか、なぜそこか。足したテスト。テスト全体の結果。
6. **残っていること**: 確かめられなかったこと、応急処置なら失われたものと残る作業。

失敗率の測定には、このスキルのディレクトリにある `scripts/repro_rate.py` を使う。作業ディレクトリは調査対象のプロジェクトのまま、スクリプトをスキルのディレクトリからのパスで指定し、`uv run` で実行する (`python3` で直接起動しない)。

```bash
uv run <このスキルのディレクトリ>/scripts/repro_rate.py -n 30 -- pytest tests/test_x.py
```
