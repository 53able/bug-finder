# 間欠的な失敗

「たまに落ちる」は、失敗を決める条件がまだ見えていないという意味である。条件を見つけて、毎回失敗させられる形にするのが最初の目標になる。

## まず数える

- `scripts/repro_rate.py` で、同じコマンドを決まった回数だけ実行して失敗率を出す。
  ```bash
  uv run <このスキルのディレクトリ>/scripts/repro_rate.py -n 30 -- pytest tests/test_tags.py
  uv run <このスキルのディレクトリ>/scripts/repro_rate.py -n 50 --timeout 60 --stop-on-fail -- python run.py
  ```
- 失敗率は、修正の効果を判定する基準になる。修正前と修正後で、回数とコマンドを揃える。
- 0 回失敗は「失敗しない」ことの証明にならない。各試行が独立で失敗率 p が変わらないと仮定すると、n 回すべて成功する確率は (1-p)^n である。p が 30% なら、20 回連続成功する確率は約 0.08% なので、改善を示す材料になる。p が 2% なら約 67% であり、20 回の成功だけでは改善を判断しにくい。修正前に測った失敗率 p > 0 を目安に、試行回数を 3/p 以上に切り上げて決めると、同じ失敗率のまま全回成功する確率は約 5% 以下になる。ただし、p 自体の推定誤差や試行間の依存は別に考慮する。
- 単独で実行したときと、スイート全体で実行したときの両方を数える。片方だけで落ちるなら、それ自体が手がかりになる。

## 実行ごとに変わるものを列挙する

失敗率が 0% でも 100% でもないなら、実行ごとに何かが変わっている。候補を挙げ、一つずつ固定して失敗率がどう動くかを見る。

| 変わるもの | 固定する方法の例 |
| --- | --- |
| 文字列のハッシュ (Python の `set` や `dict` 由来の順序) | `PYTHONHASHSEED=0` と `PYTHONHASHSEED=1` で比べる |
| 乱数 | シードを固定する。シードを出力させ、失敗した回のシードで再実行する |
| テストの実行順 | 落ちたときの順序を指定して実行する (`pytest a.py::test_x b.py::test_y`)。pytest-randomly を入れているなら `-p no:randomly` で順序を固定する |
| 時刻、日付、タイムゾーン | 時計を差し替える。`TZ` を変えて比べる。月末、日付変更、夏時間の境界で実行する |
| 並行実行のタイミング | 並行度を 1 にする、待ちを挟む、スレッド数を増やして悪化するか見る |
| 外部サービスの応答 | 応答を記録して差し替える。遅延を注入する |
| ファイルシステムの列挙順、一時ファイルの残り | 列挙結果を並べ替えて使っているか見る。毎回きれいな作業ディレクトリで実行する |
| プロセス間で共有されるもの (キャッシュ、DB、ポート) | 実行ごとに分ける |

固定した瞬間に失敗率が 0% か 100% に振れたら、それが条件である。

## テストの順序で結果が変わる場合

- あるテストが残した状態を、別のテストが読んでいる。候補は、モジュールの変数、クラス変数、関数の既定引数、シングルトン、キャッシュ、環境変数、カレントディレクトリ、一時ファイル。
- 失敗するテストの前に何を実行すると落ちるかを絞る。前に走るテストの集合を半分ずつにしていけば、汚している一つが見つかる。
- 「汚す側」と「読む側」の 2 つのテストだけで毎回落ちる組み合わせを作り、再現手順として報告する。
- テスト側で状態を毎回初期化して通すのは、症状を隠すだけである。本番のコードでも同じ状態が呼び出しをまたいで残るなら、本体を直す。

## 決定的に再現できたら

- 失敗する条件を固定したコマンドを、以後の判定に使う。例: `PYTHONHASHSEED=3 pytest tests/test_tags.py`。
- 修正後は、固定したコマンドで通ることと、固定しない元のコマンドを同じ回数繰り返して失敗が 0 件であることの両方を示す。
- 同じ非決定性に依存した書き方が他にないか探す。順序が変わる変換 (`list(set(...))` など) は、一か所で見つかれば近くに複数あることが多い。

## 測定の注意

- 繰り返し実行が外部へ副作用を出すなら、先に止める。
- 失敗のたびに出力を保存し、失敗の種類が一種類か確かめる。種類が混ざっているなら、別々の原因として扱う。
- 負荷を上げると出やすくなる失敗は、タイミングが条件である。機械の速さに依存した修正 (待ち時間を延ばすだけ) は避け、順序を保証する仕組みで直す。
