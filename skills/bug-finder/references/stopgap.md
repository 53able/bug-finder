# 応急処置

被害が続いていて、根本修正に時間がかかる、または依頼が作り直しを望んでいないときに、まず被害を止める。

## 応急処置を選ぶ条件

- 依頼に「急ぎ」「止血」「作り直しはしない」「このファイルは触らない」といった制約がある。
- 根本修正が、設計の変更や複数モジュールの作り直しを必要とする。
- 誤った出力 (在庫、請求、送信) が今も積み上がっている。

根本修正が小さく安全なら、応急処置ではなく根本修正をする。

## 手順

1. **先に症状を確かめる**: 再現コマンドかシミュレーションを実行し、現在の数値を記録する。修正後の比較に使う。
2. **原因を特定する**: 応急処置でも、何が原因かは確かめる。原因が分からないまま止めると、別の場所が壊れたままになる。
3. **止め方を選ぶ**: 次の表で、戻しやすく、巻き込む変更が少ないものを選ぶ。

   | 止め方 | 向いている場面 | 注意 |
   | --- | --- | --- |
   | 設定や機能フラグで無効にする | 切り替えの仕組みが既にある | 無効にした状態がテストされているか確かめる |
   | 呼び出し側を以前の経路に戻す | 新しい仕組みを経由する呼び出しが少数 | 新しい仕組みのモジュール自体には手を入れない |
   | 原因のコミットを取り消す | 原因が一つのコミットに収まり、後のコミットとの衝突が小さい | `git revert --no-commit <コミット>` で作業ツリーに反映し、衝突は後のコミットの意図を残して解決する。コミットは依頼があるときだけ作る |

   触らないよう指示された部分は、どの止め方でも変更しない。使われなくなったコードを消すかは依頼の範囲で判断する。
4. **応急処置であると明示する**: 変更箇所のコメント、またはコミットを作るならそのメッセージに、暫定策であること、何を止めたか、根本修正の方針を書く。
5. **同時期の正しい変更を残す**: 原因の後に入った機能や修正が消えていないことを、テストだけでなく、その機能の README やコミットに書かれた使い方のコマンドを実際に実行して確かめる。実行したコマンドと出力を報告に入れる。
6. **確かめる**: 手順 1 と同じコマンドで、数値が期待どおりになったこと、テスト全体が通ることを確かめる。

## 報告に入れること

- 応急処置であること
- 原因
- 何をして止めたか
- 失われるもの: 取り消した機能が提供していた利点 (速度、応答性、自動再試行など)
- 残る作業: 根本修正の方針 (キーの設計の見直し、冪等性の確保、回帰テストの追加など)
- 既に出てしまった誤った結果の後始末が必要か
