# 修正の作法

## 直す場所を選ぶ

- 誤りが生まれた地点で直す。誤った値を使う側で補正すると、補正していない別の使い手に誤りが残る。
  - 文字列のまま読み込まれた数値は、ソートの側ではなく読み込みの側で数値にする。
  - null が既定値を消すマージは、表示の側ではなくマージの側で直す。
  - 呼び出し間で共有される既定引数は、テストの初期化ではなく関数の側で直す。
- 直さない場所:
  - 外部から取り込んだコード (vendor、サブモジュール、インストール済みのパッケージ)。同期や更新で消える。
  - 生成物。生成元を直して生成し直す。
  - テストの期待値。期待値の方が誤っていると根拠を示せる場合だけ変える。変えたら、変えた理由を報告する。
- 同じ誤りが複数の箇所にあるなら、すべて直すか、共通の処理にまとめる。直さない箇所があるなら理由を報告する。

## 範囲を守る

- 修正は、原因を取り除くのに必要な最小限にする。ついでの整理、名前の変更、整形は別の変更にする。
- 原因のコミットを丸ごと取り消すと、同じコミットに入っていた正しい変更や、後のコミットが依存している変更まで消える。必要な部分だけ直す。
- 修正が、既に依存している呼び出し側の挙動を変えないか確かめる。挙動を変える必要があるなら、影響を報告する。
- 修正で失われるもの (性能、機能、互換性) があれば報告する。

## テストを足す

- 原因を直接突くテストを書く。症状の再現ではなく、原因の条件を突く。
  - 境界の値 (ちょうど 15 km、割り切れない件数)
  - null の上書きを持つ設定
  - 同じ関数を 2 回呼ぶ
  - ハッシュのシードを変えても順序が保たれること
- テストが、修正前のコードで失敗することを確かめる。修正を一時的に戻すか、修正前のコミットで実行する。修正前に通るテストは、原因を捉えていない。
- 実在のデータ (顧客名、テナント名) をテストに使う場合は、該当する性質だけを持つ架空のデータに置き換える。
- テスト全体を実行する。失敗したテストがあれば、修正との関係を調べて報告する。修正と無関係に元から失敗していたなら、修正前の結果と並べて示す。

## 確かめる

- 手順 2 の判定コマンドで症状が消えたことを確かめる。
- 報告された数値や出力と比べる。例: 「上位 3 件が T005, T002, T004 になった」「合計が 2970 円」。
- 間欠的な失敗なら、修正前と同じ回数で繰り返して失敗が 0 件であることを示す。
- 静かに誤っていた別の処理も、正しい結果になったことを確かめる。
- 調査用に足した出力、一時ファイル、作業ツリーを片付ける。
