# 例外の場所と原因の場所が違う

例外が起きた行は、誤った値が最後に使われた場所であって、作られた場所とは限らない。

## スタックトレースの読み方

- 例外が起きた場所は、Python では最後のフレーム、Java や C# では最初のフレームに出る。そこから呼び出し元の方向へ、自分たちのコードが最後に出てくるフレームを探す。そのフレームが、外部のコードへ値を渡した地点である。
- 外部のコード (同梱ライブラリ、標準ライブラリ、生成コード) の中で落ちていても、まず渡した値を疑う。広く使われているコードは、たいていの入力で正しく動いている。
- 渡した値が、そのコードの前提 (型、None でない、空でない、文字コード) を満たしているか確かめる。満たしていなければ、原因は値を作った側にある。
- 外部のコード自体の誤りだと判断するなら、正しい値を渡しても誤ることを示す最小の再現を作る。その場合も、外部のコードを直接書き換えずに報告し、呼び出し側で回避する。

## 値を作った地点まで遡る

- 例外が起きた値を、代入、引数、戻り値、設定の読み込み、データベース、外部の応答と、作られた地点まで遡る。
- 各段で値を確かめ、「入力は正しく、出力は誤っている」段を見つける。原因はその段の中にある。
- よくある起点:
  - 設定やデータのマージで、null が既定値を上書きする。
  - 読み込み時に型を変換していない (CSV や JSON の数値が文字列のまま)。
  - 欠けたキーを既定値で埋める処理が、一部の経路だけで抜けている。
  - 単位や桁の取り違え (秒とミリ秒、円と銭、バイトと文字数)。
  - 文字列への変換で `None` が `"None"` になる。

## 同じ値を使う他の処理を探す

- 誤った値を使っているのは、例外を出した処理だけとは限らない。同じ値を受け取る処理を列挙する。
- 例外にならずに誤った出力を出している処理がよくある。文字列に埋め込まれて `None` と表示される、ソートの順が狂う、合計がずれる。こちらの方が気づかれにくく、被害が大きいことがある。
- 起点を直したら、例外を出していた処理と、静かに誤っていた処理の両方で結果が正しくなったことを確かめる。

## 該当するデータを特定する

- 誤った値を生むデータを全件から抜き出す。例: 全テナントの設定を読み、null の上書きを持つものを列挙する。
- 該当件数と、どのデータかを報告する。影響範囲の判断と、既に出てしまった誤った出力の後始末に必要になる。
- 該当データを直して症状を消すのは応急処置である。同じ形のデータが今後入っても正しく動くように、処理の側を直す。
